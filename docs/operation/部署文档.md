# 阿米巴经营分析平台部署文档

## 1. 文档基线

- 适用仓库：`https://github.com/SoulCreators/amoeba-operation-analysis.git`
- 目标分支：`main`
- 文档更新时间：2026-10-22（Asia/Shanghai）
- 应用版本：Spring Boot `2.7.18`、JDK `8`、前端 Node.js `20`
- 数据库：PostgreSQL；当前仓库迁移编号为 `V001`–`V035`

本文以当前源码为准，适用于内网/UAT 或生产环境的手工、systemd 和容器化部署。仓库当前没有提供 docker-compose、Nginx 配置和统一认证实现，以下三部分需要由目标环境补齐。

## 2. 部署拓扑

```text
浏览器
  │ HTTPS / 统一认证
  ▼
Nginx / API 网关
  ├── 静态前端（frontend/dist）
  └── /api/* ─────► analysis-api :8080
                         │
                         ├── PostgreSQL
                         └── 共享文件根目录

analysis-worker（无对外业务端口）
  ├── PostgreSQL
  └── 与 API 共享同一个 analysis.storage.root
```

组件职责：

- `analysis-api`：批次、导入、计算、结果、配置、导出和 V1.3 查询 API。
- `analysis-worker`：仅在 `db,filesystem` 两个 profile 同时启用时运行导出文件清理任务，每 10 分钟执行一次有界清理。
- PostgreSQL：保存批次、导入任务、原始事实、配置、计算结果、审计和导出任务元数据。
- 文件根目录：当前 filesystem 适配器保存导入原文件、导入问题文件和导出文件；正式环境必须使用持久化磁盘或后续接入对象存储。

## 3. 前置条件

### 3.1 构建机

- JDK 8、Maven 3.6+。
- Node.js 20、npm。
- Git、`psql`、`pg_dump`。
- 若使用容器构建，需要 Docker 或兼容 OCI 的构建工具。

仓库提供用户级工具链约定：

```bash
source deploy/scripts/env-local.sh
```

该脚本要求仓库下存在 `.toolchain/jdk8`、`.toolchain/maven` 和 `.toolchain/node`。如果目标机器使用系统工具链，可直接使用系统的 `java`、`mvn`、`node` 和 `npm`，但必须确认版本满足上述要求。

### 3.2 运行环境

- PostgreSQL 建议使用 16.x；当前真实回归记录使用过 PostgreSQL 16.2。
- API 运行时使用 JRE 8 即可；Worker 同样使用 JRE 8。
- API 和 Worker 必须能够访问同一个 PostgreSQL 数据库。
- API 和 Worker 必须挂载同一个持久化文件根目录；两者使用不同目录会导致导出下载或清理失败。
- 生产密钥不得写入仓库、镜像或普通配置文件，应由密钥管理平台、systemd secret 或容器运行时注入。

## 4. 获取代码与发布目录

首次部署：

```bash
git clone --branch main --single-branch \
  https://github.com/SoulCreators/amoeba-operation-analysis.git
cd amoeba-operation-analysis
git rev-parse HEAD
```

后续更新必须确认工作区无未提交改动，并使用快进更新：

```bash
git status --short
git fetch origin main
git pull --ff-only origin main
git rev-parse HEAD
```

建议每个版本使用独立发布目录，例如：

```text
/opt/amoeba/releases/<commit-sha>/
/opt/amoeba/current -> /opt/amoeba/releases/<commit-sha>
/var/lib/amoeba/files/       # API 与 Worker 共享，禁止放在代码目录
```

切换版本前保留上一版本目录，确认新版本通过验收后再清理旧版本。

## 5. 数据库初始化与迁移

当前项目没有 Flyway/Liquibase，Spring Boot 启动不会自动执行迁移。必须由发布流程使用 `psql` 按编号顺序执行 `database/migration/` 下的 SQL。

### 5.1 迁移前备份

在首次初始化、升级或执行回滚前先备份：

```bash
pg_dump --format=custom \
  --host "$DB_HOST" \
  --port "${DB_PORT:-5432}" \
  --username "$DB_USER" \
  --dbname "$DB_NAME" \
  --file "/secure/backup/amoeba_$(date +%Y%m%d%H%M%S).dump"
```

密码应通过 `PGPASSFILE` 或密钥管理平台提供，避免把密码直接写入命令行和 shell 历史。

### 5.2 执行全部迁移

确认数据库、账号和备份无误后，在仓库根目录执行：

```bash
for migration in database/migration/V*.sql; do
  echo "Applying ${migration}"
  psql -v ON_ERROR_STOP=1 \
    --host "$DB_HOST" \
    --port "${DB_PORT:-5432}" \
    --username "$DB_USER" \
    --dbname "$DB_NAME" \
    --file "$migration"
done
```

当前迁移顺序为 `V001` 到 `V035`。已执行的迁移文件禁止修改；结构变更必须新增更大的版本号，并同步提供验证脚本和回滚说明。

### 5.3 初始 ADMIN 引导

`V035` 只创建 `ADMIN` 角色，不会猜测或自动提权任何生产用户。统一认证能稳定提供 `Principal` 后，数据库管理员必须将经审批的首位管理员主体写入主数据并授予 `ADMIN`：

```sql
INSERT INTO iam.platform_user
    (user_id, employee_no, username, display_name, enabled, created_by, updated_by)
VALUES
    ('<SSO_PRINCIPAL>', '<EMPLOYEE_NO>', '<LOGIN_NAME>', '<DISPLAY_NAME>', TRUE, '<OPERATOR>', '<OPERATOR>')
ON CONFLICT (user_id) DO UPDATE SET
    employee_no = EXCLUDED.employee_no,
    username = EXCLUDED.username,
    display_name = EXCLUDED.display_name,
    enabled = TRUE,
    updated_by = EXCLUDED.updated_by,
    updated_at = CURRENT_TIMESTAMP;

INSERT INTO iam.user_role(user_id, role_code, enabled, created_by, updated_by)
VALUES ('<SSO_PRINCIPAL>', 'ADMIN', TRUE, '<OPERATOR>', '<OPERATOR>')
ON CONFLICT (user_id, role_code) DO UPDATE SET
    enabled = TRUE,
    updated_by = EXCLUDED.updated_by,
    updated_at = CURRENT_TIMESTAMP;
```

占位符必须替换为目标环境真实且已审批的值，执行后由第二人复核。`local` Profile 会自动为 `local-finance` 初始化本地联调角色，不得在生产环境启用。

### 5.3 结构验证

```bash
for check in database/verification/check_*.sql; do
  echo "Checking ${check}"
  psql -v ON_ERROR_STOP=1 \
    --host "$DB_HOST" \
    --port "${DB_PORT:-5432}" \
    --username "$DB_USER" \
    --dbname "$DB_NAME" \
    --file "$check"
done
```

至少应确认基础 schema、导入任务、结果、事实追溯、导出任务、审计、清理生命周期和配置导入问题表均通过验证。

### 5.4 回滚边界

仓库目前只提供 `V018`–`V024` 的手工回滚脚本。`V001`–`V017` 没有对应的通用回滚脚本，不能假设可以逆向删除；如需回退，应优先使用备份恢复或经过评审的前向修复迁移。

执行 `database/rollback/` 下脚本前必须：

1. 停止 API 和 Worker，避免应用继续访问待删除对象。
2. 确认没有后续迁移或代码依赖目标表/字段。
3. 完成数据库备份并获得人工审批。
4. 按目标版本倒序执行，并重新执行相关 verification 脚本。

## 6. 构建产物

### 6.1 后端

```bash
mvn -B -s deploy/config/maven-settings.xml \
  -Dmaven.repo.local="${MAVEN_REPO_LOCAL:-.toolchain/m2}" \
  clean package
```

构建产物：

```text
backend/analysis-api/target/analysis-api-0.1.0-SNAPSHOT.jar
backend/analysis-worker/target/analysis-worker-0.1.0-SNAPSHOT.jar
```

### 6.2 前端

生产前端默认通过同域 `/api/v1` 调用 API，因此推荐由 Nginx 将 `/api/` 反向代理到 API 的 `8080` 端口：

```bash
cd frontend
npm ci
npm run test:unit
npm run build
```

产物目录为 `frontend/dist/`。如 API 使用独立域名，必须在构建时设置 `VITE_API_BASE_URL`，例如：

```bash
VITE_API_BASE_URL=https://finance.example.com/api/v1 npm run build
```

`VITE_API_BASE_URL` 是构建时变量，不是运行时变量；修改后必须重新构建前端。

### 6.3 Docker 镜像

仓库只提供 API 和 Worker Dockerfile，没有前端镜像和编排文件。后端镜像应以仓库根目录为构建上下文：

```bash
docker build -f deploy/docker/Dockerfile-api \
  -t registry.example.com/amoeba/analysis-api:<commit-sha> .

docker build -f deploy/docker/Dockerfile-worker \
  -t registry.example.com/amoeba/analysis-worker:<commit-sha> .
```

两个镜像都依赖先完成 Maven 打包。发布前将镜像推送到企业镜像仓库，并记录镜像 digest；不要使用浮动的 `latest` 作为生产回滚依据。

## 7. 生产配置

### 7.1 API

生产 API 应启用 `db,filesystem`，不要启用 `local`：

```bash
export SPRING_PROFILES_ACTIVE=db,filesystem
export AMOEBA_DB_URL='jdbc:postgresql://db.example.internal:5432/amoeba_analysis'
export AMOEBA_DB_USERNAME='由密钥管理平台注入'
export AMOEBA_DB_PASSWORD='由密钥管理平台注入'

java -jar backend/analysis-api/target/analysis-api-0.1.0-SNAPSHOT.jar \
  --server.port=8080 \
  --analysis.storage.root=/var/lib/amoeba/files
```

`analysis.storage.root` 同时用于 API 的导入文件和导出文件适配器。API 与 Worker 必须配置为同一个目录，并确保运行账号具备读写权限。

### 7.2 Worker

Worker 只有在 `db` 和 `filesystem` 两个 profile 同时启用时才会注册清理任务：

```bash
export SPRING_PROFILES_ACTIVE=db,filesystem
export AMOEBA_DB_URL='jdbc:postgresql://db.example.internal:5432/amoeba_analysis'
export AMOEBA_DB_USERNAME='由密钥管理平台注入'
export AMOEBA_DB_PASSWORD='由密钥管理平台注入'
export ANALYSIS_STORAGE_ROOT=/var/lib/amoeba/files
export ANALYSIS_WORKER_ID=analysis-worker-01
export ANALYSIS_WORKER_CLEANUP_BATCH_SIZE=100

java -jar backend/analysis-worker/target/analysis-worker-0.1.0-SNAPSHOT.jar
```

清理行为：每 10 分钟领取一批过期导出任务；单任务失败按 5 分钟、10 分钟重试，达到终止条件后记录告警。Worker 当前不实现 S3/OSS，文件根目录必须是本地或共享挂载目录。

### 7.3 不得使用的配置

- `SPRING_PROFILES_ACTIVE=local`：只用于本地联调，使用内存适配器并将 `X-User-Id` 转成本地 `Principal`。
- `local` 与 `db` 混用：`local` 会排除 DataSource 自动配置，不应作为生产数据库 profile。
- 只启用 `db` 或只启用 `filesystem`：不会启动导出清理 Worker。
- 将真实数据库密码、认证 Token、AI 密钥、生产数据或财务文件提交到 Git。

## 8. 认证与网关要求

当前后端没有在仓库内实现公司统一认证。除 `GET /api/v1/health` 等健康检查外，大多数接口要求 Servlet 容器提供非空 `Principal`；生产环境必须由统一认证网关、容器认证适配器或企业 SSO 接入完成身份注入。

前端代码会自动发送 `X-User-Id`，但该行为仅用于本地联调。生产环境不能把这个请求头当作可信身份来源，也不能允许客户端自行伪造用户工号。网关应完成：

- HTTPS 终止和统一登录；
- 清理或覆盖外部传入的伪造身份请求头；
- 将已验证主体注入后端 `Principal`；
- 按企业认证规范传递角色、范围和审计信息；
- 仅对健康检查放开匿名访问。

## 9. 反向代理与静态前端

仓库没有提交 Nginx 配置。生产环境至少需要具备以下路由语义：

```nginx
server {
    listen 443 ssl;
    server_name finance.example.com;

    root /opt/amoeba/current/frontend/dist;

    location /api/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        # 认证网关在此之前完成主体校验，不信任浏览器自行提交的身份头。
    }

    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

如果使用独立认证网关，应由网关负责认证和 `/api/` 转发；不要直接把 API 暴露到公网。

## 10. 启停与健康检查

### 10.1 启动顺序

1. 确认 PostgreSQL 可连接并完成迁移和 verification。
2. 创建共享文件根目录并设置最小权限。
3. 启动 API。
4. 通过网关完成认证链路检查。
5. 启动 Worker。
6. 部署前端静态文件并执行浏览器 smoke。

### 10.2 API 健康检查

```bash
curl --fail --silent http://127.0.0.1:8080/api/v1/health
curl --fail --silent http://127.0.0.1:8080/actuator/health
```

第一个接口应返回 `status=UP` 的业务响应。第二个接口由 Spring Boot Actuator 提供。健康检查通过不代表数据库迁移、认证和业务数据已验收，仍需继续执行发布 smoke。

### 10.3 业务 smoke

应使用已接入认证的测试账号，通过网关验证：

- 创建/查询测试批次；
- 查询批次 readiness 和 quality；
- 上传一份脱敏 XLSX 并确认校验结果；
- 执行计算、确认、发布生命周期；
- 查询结果、PVM、指标树和 V1.3 接口；
- 创建导出任务并下载文件；
- 检查 Worker 日志中没有数据库连接、文件根目录或清理失败异常。

禁止用 `X-User-Id` 伪造生产认证来替代上述验收。

### 10.4 计算失败重试与日志追踪

- 当前 `POST /api/v1/calculations` 在 API 进程内同步执行计算；失败时将批次置为 `FAILED` 并抛出错误。
- 当前 Worker 只负责导出文件清理，不消费计算任务；仓库也没有可用于生产计算重试的持久化计算任务队列或调度器。
- 计算失败后应先修复导入数据、配置或数据库问题，再由已授权用户通过同一个计算接口重新发起；不要直接修改数据库中的结果或批次状态。
- 已确认或已发布批次禁止直接重算。若进程异常导致批次长期停留在 `CALCULATING`，应按故障处理，先保留日志和数据库现场，再由研发/数据库负责人评估恢复方案。
- 导出清理 Worker 自带 5 分钟、10 分钟两次重试和终止告警；这套重试不适用于计算、AI 或导入任务。
- systemd 部署使用 `journalctl -u amoeba-analysis-api` 和 `journalctl -u amoeba-analysis-worker` 追踪日志；容器部署使用运行平台的 stdout/stderr 日志采集。日志中不得输出密码、Token、完整财务明细或上传文件内容。
- 当前仓库没有提交集中式日志、告警规则和完整 trace 采集配置，生产平台需补充 API 5xx、数据库连接失败、导入失败、计算失败、导出失败和 Worker 终止清理任务告警。

### 10.5 停止顺序

```bash
停止前端流量
停止 Worker
停止 API
```

数据库迁移或回滚时必须先停止 API 和 Worker，避免迁移期间继续读写业务表。

## 11. 发布更新流程

每次发布建议按以下顺序执行：

1. 记录待发布 commit、镜像 digest 和数据库当前版本。
2. 备份 PostgreSQL。
3. 拉取目标 `main` 提交并校验工作区干净。
4. 在构建机执行后端构建、前端依赖安装、前端单测和生产构建。
5. 在隔离环境执行数据库迁移和 verification。
6. 发布 API 和 Worker 新版本；保留上一版本可回滚。
7. 切换前端静态资源和流量。
8. 执行 API 健康检查、认证检查和脱敏业务 smoke。
9. 观察 API/Worker 日志、数据库连接、导入和导出任务。
10. 在发布记录中写入 commit、迁移版本、镜像 digest、验收结果和已知风险。

当前 `main` 最新提交是导出 Worker 回归测试提交；本次拉取和文档生成没有修改业务源码，也没有执行生产数据库迁移。

## 12. 常见问题

### API 启动时报 DataSource 或 PostgreSQL 驱动错误

确认已执行 `mvn clean package`，API jar 包含 PostgreSQL runtime 依赖；确认 `SPRING_PROFILES_ACTIVE` 包含 `db`，且 `AMOEBA_DB_URL`、用户名和密码已注入。

### API 启动成功但业务接口返回未认证

这是因为生产代码依赖容器 `Principal`。检查统一认证网关、反向代理和容器认证配置，不要通过放开 `X-User-Id` 解决。

### 导出下载失败或 Worker 清理不到文件

确认 API 的 `--analysis.storage.root` 与 Worker 的 `ANALYSIS_STORAGE_ROOT` 完全一致，且两个运行账号对目录有读写权限；检查共享挂载是否在两个实例中可见。

### Worker 启动了但没有清理任务

确认同时启用了 `db,filesystem`。只启用一个 profile 不会注册 `ExportCleanupWorker`。

### 数据库迁移重复执行

仓库没有迁移版本表，SQL 主要使用 `IF NOT EXISTS`，但不能把重复执行当作正式迁移管理方案。生产应由发布平台记录已执行 commit/迁移版本，并在执行前人工核对数据库结构。

### 前端仍然访问旧 API

检查构建时的 `VITE_API_BASE_URL`、浏览器缓存和 Nginx `/api/` 路由。修改环境变量后必须重新执行 `npm run build` 并替换 `frontend/dist`。
